El viaje de un request

Todos los sistemas tienen un cuello de botella. La entrevista de system design es saber encontrarlo antes de que te lo encuentren.

01

La idea

Un request viaja: cliente → load balancer → app servers → base de datos. Cada pieza tiene una capacidad máxima. Mientras el tráfico quepa, todo va fino; en cuanto una pieza se satura, los requests se encolan, la latencia explota y algunos mueren.

La regla de oro: el sistema va tan rápido como su pieza más lenta. Escalar cualquier otra es decorar.

02

03

La matemática

L = λ · W  (Ley de Little)

Requests en el sistema = tasa de llegada × tiempo de respuesta. Con λ=800 rps y W=120 ms: 96 requests en vuelo. Si la pieza que menos aguanta tiene capacidad para 60 concurrentes, el resto se encola o cae. Utilización > 70% y la cola crece sin cota — por eso el tráfico “que cabe en promedio” aún tumba sistemas en los picos.

04

El código

import heapq, random

def simulate(rps, capacity, seconds=60):
    """Cola M/M/c minimal: servidor que atiende 'capacity' req/s."""
    departures = []          # heap de tiempos de salida
    dropped = 0
    for t in [i / rps for i in range(int(rps * seconds))]:
        while departures and departures[0] <= t:
            heapq.heappop(departures)
        if len(departures) < capacity:
            heapq.heappush(departures, t + random.expovariate(1))
        else:
            dropped += 1
    return dropped

Una cola en 15 líneas: todo el drama de system design es una llegada contra una capacidad.

05

En el trabajo real

En la entrevista de system design te piden “diseña Twitter”: lo que evalúan no son las cajas que dibujas sino si calculas dónde se satura primero — QPS de lectura vs escritura, fan-out, y qué rompe cuando una pieza cae.

En producción: esto es SRE básico. Capacity planning = estimar λ, medir W, y poner el cuello donde sea barato y visible (cola explícita) en vez de implícito (timeouts en cadena).

06

Check yourself

Tu app server aguanta 400 rps y llegan 600 rps sostenidos. ¿Qué pasa con la latencia?

Con llegadas sostenidas > capacidad, la cola crece cada segundo: utilización > 1 no se estabiliza nunca. En la vida real algo cede primero (timeouts, memoria, el cliente que se rinde).

Tu DB es el cuello y el 80% de lecturas se repiten. ¿Qué cambio baja más la carga?

Más app servers escala la pieza equivocada: la DB sigue saturada. El cache ataca directo el cuello — si 80% de lecturas se repiten, la DB ve una fracción del trabajo.
